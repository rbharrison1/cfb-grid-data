# cfb-grid-data

Data pipeline for cfbgrid.com. Three independent Cloud Run services live in this one repo:

- **Ingest** (root of this repo — `app.py`/`bq_ingest.py`, service `cfb-grid-ingest`, public): pulls from the CFBD API + a fbschedules.com scrape, lands raw NDJSON in GCS, loads it into BigQuery `raw_*` tables (`WRITE_APPEND`, deduped by `_ingested_at` on read — see README for the endpoint table).
- **Transform** (`transform/` — `app.py`/`bq_transform.py`, service `cfb-grid-transform`, private): reads the `raw_*` BigQuery tables, merges/enriches, and writes final per-timezone game documents into MongoDB `cfb-grid.games` (or `games_test` for testing). This is what `cfb-grid-server` actually serves.
- **Live scores** (`live-scores/` — `app.py`, service `cfb-grid-live-scores`, private): a poller, scheduled every minute during game windows (see Daily/live automation below), with no BigQuery involvement at all. Fetches both the `fbs` and `fcs` NCAA scoreboard divisions (github.com/henrygd/ncaa-api, public demo at `ncaa-api.henrygd.me` — the Mongo grid isn't FBS-only, since CFBD ingest doesn't filter by classification), matches games to existing Mongo docs by team name across the whole season (NCAA shares no id with CFBD), and patches `live_*` fields directly onto them. See its own module docstrings (`app.py`, `team_match.py`, `mongo_patcher.py`) for the design. **Writes to production `games`** (`MONGO_COLLECTION=games` set on the deployed service) as of 2026-09-17, confirmed working end-to-end on a real live game (Syracuse @ Pittsburgh) the same night.

Feeds into: [`cfb-grid-server`](../../cfb-grid-server/CLAUDE.md) reads the `games` collection this writes to. See the [workspace map](../../CLAUDE.md) for the full chain.

## Deployment — manual, not CI/CD

`.github/workflows/deploy.yml` exists but its Google Cloud OIDC auth is currently broken and has apparently never worked. Deploys are done by hand:

```bash
cd cfb-grid-data/cfb-grid-data && gcloud run deploy cfb-grid-ingest --source . --region us-central1 --project <project>
cd transform && gcloud run deploy cfb-grid-transform --source . --region us-central1 --project <project>
```

The README's Deployment and Transform service sections cover the same ground in more detail (endpoint params, env vars, full deploy/scheduler commands) — this file just holds the "why," not the "how."

## Non-obvious gotchas (all verified against real production incidents this repo has had)

- **gunicorn `--timeout` must be set explicitly in the Dockerfile `CMD`.** Left unset, it silently defaults to 30s and caps every request — this cost a real debugging session before being traced to the Dockerfile rather than the app code. Both Dockerfiles now set `--timeout 1800`, matching each Cloud Run service's own `--timeout=1800` (two independent settings — Cloud Run's request timeout and gunicorn's worker timeout — both have to be raised for long requests).
- **Never use `x or default` to read a `week` param — check `is None` explicitly.** `week=0` is a real, valid CFB week and is falsy in Python, so `or`-chaining silently drops it to the default and re-ingests the wrong week. See `_param()` in both `bq_ingest.py` and `transform/app.py`.
- **CFBD's `week=1` covers two fbschedules.com weeks.** fbschedules.com has a separate "Week 0" (season-opening games, e.g. Ohio Dominican @ Morehead State) and "Week 1", but CFBD folds both into its own `week=1`. `fbschedules.py`'s `_fbschedules_weeks_for_cfbd_week()` fetches both fbschedules weeks and merges them under CFBD's week=1; every week ≥2 maps 1:1. If you're aligning any other CFBD-vs-fbschedules data, check this function first — it's the one place this mismatch is handled.
- **The grid re-splits that same week=1 bucket back into week 0 vs week 1, by date.** `bq_transform.py::_split_off_week_zero` runs after the fbschedules date/time correction and overrides `week` to `0` for any week=1 game whose corrected Eastern kickoff date is Aug 27–30 inclusive; everything else in that bucket stays `week=1`. This means a single `/transform?week=1` call can produce both week-0 and week-1 Mongo documents — `app.py::_transform_one_week` handles this by writing (and clearing the stale slot for) both `week=0` and `week=1` in Mongo whenever the request's `week` is `1`, rather than assuming the request's week param is the only slot touched. `get_team_schedule`'s per-opponent schedule entries are **not** re-split (they read the season-wide `raw_all_games` snapshot directly, still CFBD's raw week numbering) — a team's own schedule popup will still show `week: 1` for its opener even though the main grid shows it under week 0. cfb-grid-server and cfb-grid-web both handle `week: 0` with no changes needed (verified: neither has a truthy/falsy check or hardcoded week range that would drop it).
- **A single long-running `week=all` transform request reliably gets its connection dropped**, even though the server-side work completes correctly (verified via direct Mongo inspection both times it happened). Flask/gunicorn buffer the entire response and emit nothing until the view function returns, and something upstream (Google's infra) drops idle-looking connections after a few minutes of silence — this is shorter and less predictable than the actual configured request timeout. Root cause of the daily job design below: **don't reintroduce a single `week=all` HTTP call on a schedule** — call `/transform` per-week instead, or if you need `week=all` again, make it stream/checkpoint rather than buffering one giant response.
- **Mongo writes are delete-then-insert scoped to `(season, week, timezone)`, not "delete only games present in the new payload" — except a game already stored as `completed: true` is frozen and never touched again.** If you filter which games get written (e.g. null outlet, unmapped network) without wiping the whole slot first, stale docs from a previous run accumulate silently — this happened for real (1086 stale null-outlet docs) before `mongo_writer.write_to_mongodb`'s delete was changed to `delete_many({'season', 'week', 'timezone'})` on every overwrite. The freeze exception (added later) only deletes/reinserts the *not-yet-completed* docs in a slot: `write_to_mongodb` reads the `game_id`s already stored `completed: true` for that slot and both excludes them from the delete filter and drops them from the fresh insert batch, so a completed game keeps forever whatever score/status/record it had the run it first showed `completed: true`. This depends on `game_id` (CFBD's own game id, added to every document in `bq_transform.py::format_game_data`) being present and stable — don't remove it.
- **BigQuery's load-job `autodetect` permanently locks a column's type from the first batch that has any data in it — including an all-null batch, which defaults to `STRING`.** CFBD's game rows have `null`/`[]` for every post-game stat field (scores, elo, win probability, line scores, `expectedWins`, etc.) until a game actually finishes; the very first ingest of the 2026 season landed before any game had a result, so BigQuery inferred those columns as `STRING`. Once real games started finishing days later, every append silently failed with e.g. `Field homePoints has changed type from STRING to INTEGER` — `ALLOW_FIELD_ADDITION`/`ALLOW_FIELD_RELAXATION` don't cover a type change on an existing column, and BigQuery has no "widen this column" option. Because `bq_ingest.py`'s `_land_and_load_rows` catches this per-endpoint and the outer handler always returns HTTP 200 regardless, the daily ingest job silently stopped landing new `games`/`records`/`all_games` rows for days while reporting success. Fixed by having `_land_and_load_rows` recursively strip `None`/`[]` values from each row before landing (`_strip_empty`) — a field with no real value anywhere in a batch is never given a type at all, so it's added fresh via `ALLOW_FIELD_ADDITION` (with the correct inferred type) the first time real data shows up, instead of conflicting with a wrongly-locked one. This only prevents *new* drift; a table that already has a bad column baked in needs a one-time `CREATE OR REPLACE TABLE ... AS SELECT * EXCEPT(...)` to drop it before appends will succeed again. If `/ingest` is ever returning 200 but a `raw_*` table's data looks stale, check the response body's per-key `"error"` field before assuming the job actually ran clean — a 200 status alone doesn't mean anything landed.
- **Games are dropped from Mongo entirely, by design, if:** `outlet` is null (no TV info from either CFBD or fbschedules), or `outlet` doesn't map to a `NETWORK_COLUMNS` grid column in `transform/config/networks.py`. Both filters are in `transform/bq_transform.py`'s `generate_game_list`. This is intentional — the grid should only ever contain placeable games — not a bug to "fix" if you see fewer Mongo docs than raw games.
- **fbschedules.com is the source of truth for outlet, date, and time — not just a supplemental filler.** `bq_transform.py::_apply_fbschedules_schedule` overrides CFBD's `startDate` with fbschedules' date+time whenever fbschedules has a parseable value, even when CFBD's own time looks like a real (non-midnight) kickoff — this used to only fire for CFBD's startTimeTBD midnight placeholder, but CFBD's date/time is wrong often enough outside that case that fbschedules now wins outright. The fallback to CFBD is per-field: no parseable fbschedules time (missing, or a literal `'TBD'`) means CFBD's `startDate` is left untouched entirely; a parseable time with no parseable date keeps CFBD's own Eastern calendar date and only replaces the time-of-day. Outlet has matched this precedence (fbschedules wins when matched, CFBD is the fallback) all along — see `tv_schedule_match.py::match_outlets`.
- **Rankings come from CFBD's `"AP Top 25"` poll**, keyed by CFBD's own week numbering (`transform/bq_reader.py::read_ap_top25_rankings`). CFBD's rankings weeks align 1:1 with its games weeks with no separate week-0 poll, so the week-1 poll (effectively preseason) is already correct for the fbschedules week-0+1 merge described above — no extra special-casing needed here.
- **The NCAA scoreboard API's `week` URL segment must be zero-padded to 2 digits.** `live-scores/ncaa_client.py` calls `GET /scoreboard/football/{fbs,fcs}/{year}/{week:02d}/all-conf`. An unpadded single-digit week (`2` instead of `02`) doesn't 404 or error — it silently falls back to returning whatever the *current* live scoreboard is, regardless of the year/week actually requested. Verified by hand: unpadded weeks 0–5 all returned byte-identical "current" data; `02` correctly returned that specific weekend's games. There's no status code or response field that flags the fallback — getting this wrong means silently patching the wrong week with no visible error.
- **NCAA's own "week" numbering doesn't line up with Mongo's `week` field, and `live-scores/team_match.py::build_game_lookup` deliberately does not try to map one onto the other — it matches team-name pairs across the *whole season* instead.** Two confirmed problems with a week-scoped lookup: (1) the CFBD week=1-covers-two-weeks split above means a game NCAA reports under "week 01" might be stored in Mongo under `week=0`; (2) NCAA's "week 01" bucket turned out to be *wider* than that — it included a real 09/05/2026 game that Mongo doesn't file under week 0 or week 1 at all. There's no fixed offset to special-case; scoping the lookup to `season` only sidesteps the whole problem, since a team essentially never plays the same opponent twice in one season. `mongo_patcher.patch_live_games`'s update filter matches on `game_id` + `season` only for the same reason — it deliberately does **not** filter on `week`, since the resolved `game_id` may live in a different Mongo week slot than whatever NCAA week number triggered the poll. Separately, NCAA and Mongo also occasionally disagree on which side is "home" for the same real game (confirmed: NCAA's "Howard Alabama A&M" vs Mongo's stored `(away='Alabama A&M', home='Howard')`) — `match_ncaa_games` tries the reversed `(home, away)` pair before giving up on a game.
- **The NCAA `fbs` and `fcs` scoreboard feeds overlap** — any game where either side is an FCS team appears in *both* divisions' responses (confirmed: 37 of 86 `fbs`-feed games for 2026 week 2 also appeared in the `fcs` feed, sharing the same NCAA `gameID`). `ncaa_client.fetch_all_divisions` dedupes by `gameID` before matching; skipping this produces double writes (harmless since the patch is idempotent, just wasted work and inflated diagnostic counts).
- **`live-scores`'s `live_*` fields only persist while a game sits in Mongo as not-yet-`completed`.** `mongo_writer.write_to_mongodb`'s freeze logic (see the delete-then-insert gotcha above) only protects docs already `completed: true` *before* a given transform run starts. A game patched with `live_away_points`/`live_period`/`live_clock`/`live_status`/`live_updated_at` today (still `completed: false`) gets those fields wiped the next time the daily batch transform picks it up as newly `completed: true` — the doc is deleted and reinserted fresh via `format_game_data`, which has no `live_*` fields. This is expected, not a bug: `live_*` is a transient best-effort overlay meant to exist from kickoff until the next morning, at which point CFBD's authoritative final score/state takes over via the normal pipeline.

## Daily automation

- `cfb-grid-daily-ingest` — Cloud Scheduler, 5:00 AM America/New_York, `week=all` against `/ingest`.
- `cfb-grid-daily-transform-week-01` through `-15` — Cloud Scheduler, 6:00–6:28 AM America/New_York staggered 2 min apart, one `/transform` call per week. Deliberately *not* a single `week=all` scheduled job — see the connection-drop gotcha above. If you need to re-run everything by hand, triggering all 15 jobs back-to-back (`gcloud scheduler jobs run cfb-grid-daily-transform-week-NN`) is fine; they'll queue on Cloud Run and finish within the 300s `attempt-deadline`, just with higher latency (~1–3 min each under contention) than when spread out.

## Known gaps (not yet built, surfaced but not requested)

- Bowls/postseason games aren't covered — ingest doesn't pass `seasonType`, and the fbschedules scrape doesn't handle its bowl-schedule page.
- Raw BigQuery tables grow unbounded under daily re-ingestion — no retention/partitioning policy yet.
- `cfb-grid-live-scores`'s 4 Cloud Scheduler jobs (`cfb-grid-live-scores-thu-fri`, `-sat`, `-sat-late`, `-tue-wed`) run every minute in their respective windows (Thu/Fri evening, Saturday, the Sat-night tail into early Sunday, and Tue/Wed evening for week-6-onward MACtion) — none of which cover bowl season or conference championship weekend, same gap as above.
- `live-scores/team_match.py`'s `NCAA_NAME_ALIASES` is seeded from `games_test` runs against 2026 weeks 1–2 (288/339 matched, 85%) plus real production traffic as later weeks air — expect more entries to be needed as later weeks/conferences get polled for the first time. There's no 2025 (or earlier) season data in BigQuery at all, so historical-season testing isn't possible, only the current season's already-played weeks.
- The real in-progress `live_status` value is confirmed as `"live"` (via `games_test`/production testing, first observed 2026-09-17 on Syracuse @ Pittsburgh) — `app.py`'s `gameState != "pre"` actionable filter and `getGameLiveState`'s denylist on the `cfb-grid-web` side both already handle this correctly (they were written to not assume a specific in-progress string), so no code change was needed once this was confirmed.

## Testing

Never write to the production `games` Mongo collection or the production BigQuery dataset without explicit sign-off. Pass `collection=games_test` to `/transform` and a scratch `dataset` param to `/ingest`/`/transform` to verify changes first.
